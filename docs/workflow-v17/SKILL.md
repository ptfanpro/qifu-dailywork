# 祈福每日工作流（规则 V17）

## 必读资料

执行真实业务前完整读取：

- `references/workflow.md`：严格顺序、目录闭环、人工确认点和登录保活。
- `references/workflow.json`：机器可读规则、名称映射、时间门槛和数值限制。
- `references/performance-audit.md`：每次任务的速度目标、时间埋点、超时处理和结束后自我审计；每次真实任务都必须读取。

照片与 PDF 页面无法唯一匹配时，再读取 `references/pdf-layout-example.md`；不要把样例编号段套用到其他日期。

## 日期与固定顺序

开始前分别确定：北京时间执行时间 `E`、照片业务日期 `B_photo`、可选的 PDF 业务日期 `B_pdf`。不得根据早晚或 `E` 自动推断另外两个日期。

1. 初始化先扫描历史照片断点、待补编号清单和各日期 `1` 文件夹中的新增原图；存在多个未闭环日期时，优先定位最早日期，再逐日处理。每批 `B_photo` 可以是当天、前一天或其他补处理日期，不受 10 点限制，且不得按执行日改写实际业务日期。
2. 先解析 `B_photo` 的全部源 PDF。读取首尾完整编码、页数及少量中间锚点；只有编号区间与页数相符且锚点连续时，才生成中间页索引。条件不成立时逐页读取，绝不填补或伪造编号。若全批除一页外恰好构成唯一连续编号全集，且异常 OCR 仅为一位字符混淆，可用连续全集唯一缺口修复该页并保留离群修复证据；真实导出缺号或存在多个候选时禁止修复。
3. 照片匹配使用分级快速路径：先独立读取照片数字；高置信数字在 PDF 唯一区间内时直接定位。数字可能混淆（尤其 6/8）时比较姓名、供养物和版式等文字特征；仍不唯一时才运行页面形状指纹。相邻两个可靠数字锚点在同一拍摄模板且方向唯一时，可扩展连续序列。竖版同色牌位只有在剩余照片数、剩余 PDF 页数完全相等、无强 OCR 冲突且场景已排除时，才按 PDF 批次页序与连续拍摄顺序一一补齐。最终做一次全局一一对应、重复和缺失检查。数字/文字与指纹冲突或证据不足时停止，绝不猜号；仅有照片缺失时不阻断已唯一匹配部分，先完成其重命名、预处理和上传，并保存待补编号。清晰照片不重复运行完整指纹或二次人工核查。
4. Photoshop 动作先在副本验证，再在 `B_photo\1` 原位处理。福单按编码末段命名；供灯依次为 `2.1.jpg`、`2.2.jpg`，供水依次为 `2.5.jpg`、`2.6.jpg`。场景图必须按真实视觉类别分组，禁止因为刚好有 4 张就强制拆成 2 灯+2 水；若识别为 3 灯+1 水等超出命名上限，先完成可唯一编号的福单计划并明确提示多余场景图，绝不把场景图转成福单编号。
5. 上传并核对 `B_photo` 的图片、匹配数和场景图。上传回执按文件名和 SHA-256 逐张保存；补图后只识别、处理和上传新增文件，不重复处理已有纯数字成品或已有上传凭据的文件。照片未齐时，不等待整批补齐：严格按原 `B_photo`、福单图“已上传”和订单仍可处理筛选现有订单，上传其场景图并批量完成；福单图“未上传”的订单保持原状态，后续补图只处理新增图片和剩余订单。历史补录的供灯/供水场景图必须来自原 `B_photo` 的 `M月D日\1`，不得使用执行当天或其他日期目录里的场景图；在打开浏览器前和真正选择文件前各校验一次真实路径，目录不符立即停止，并把场景图来源日期、路径、文件名和 SHA-256 写入回执。每批以图片集合哈希和订单 ID 哈希留回执，整个日期只有在线上“福单未上传”为 0 时才闭环。历史补图可沿用旧 PDF 原编号，也可来自同一历史业务日期重新导出的新 PDF/新编号；只有线上“福单未上传”为 0 时，才能把残留旧 PDF 编号记为已由重发/重导出结果替代。点击上传前先监听浏览器文件选择器并直接设置绝对文件路径；普通上传/导出确认框在用户已明确授权本次任务时自动确认，随后以文件数、匹配数或下载结果验证。除续费“代理已处理”已有长期自动授权外，试运行中的其他终态变更仍保留一次用户确认。
6. 仅当本次任务明确包含 `B_pdf` 时才检查北京时间。早于 10:00 时明确提示“还不到北京时间10点”；晚间“当日照片模式”无论几点都跳过 PDF，不做时间检查后自动追加。
7. 达到 10:00 后导出并核对明确的 `B_pdf` PDF，保存到其 `M月D日` 文件夹；成功后确保其中存在 `1` 文件夹。若 `1` 已因当日回传照片提前存在，必须保留。续费 PDF 通过结构、页数、文件哈希和原始订单 ID 清单校验后，自动把该清单对应记录改为续费已处理终态并复核原订单 ID 已全部离开未处理。站点可能显示“延续已处理”“代理已处理”或“已处理”：若按钮直接打开明确的“批量修改成…已处理状态”确认框则直接确认；若弹窗包含状态下拉框则只在可见弹窗内部明确选择终态，禁止误用页面筛选下拉框。提交期间新到的订单保留为下一批。失败时保留 PDF 凭据，下次只补做状态变更。
8. 只汇总 `B_pdf` 当天实际纳入最终导出 PDF 的唯一订单；不得统计照片上传、状态操作日记录、重复导出或未进入最终 PDF 的文件。线下文案不带括号说明。

上传结果只读取原生弹窗或明确消息层，不读取普通弹窗全文、控件脚本或隐藏 DOM；系统同时返回本批数和累计数时，只要明确数字消息中出现本批精确文件数即采用本批数，不得用最后一个累计数字覆盖。旧式完整回执在文件集合哈希和数量一致时自动补齐逐文件哈希明细。

## 性能目标与强制审计

- 正常目标：照片专用 5–10 分钟、PDF 专用 3–6 分钟、完整闭环 10–15 分钟；目标是明显快于熟练人工的 20–30 分钟。
- 在第一次文件或浏览器操作前启动 `scripts/track_workflow_timing.py`，对每个阶段开始/结束、关键计数器、重试、人工介入和等待分类埋点。
- 达到目标时间 80% 时主动检查重复等待、重复验证和不必要的全量指纹；达到阈值后禁止新增同类重试，只做安全收尾并报告异常。
- 每次任务结束必须生成 `timing-audit.json`，报告总耗时、最慢阶段、浏览器重连、人工文件选择/确认、下载等待、重复验证和下一次一至三项优化。
- 不得用“页面响应慢”代替证据；必须区分业务系统、浏览器控制、本地计算、人工等待和重复操作耗时。
- 性能日志只记录匿名计时和计数，不得包含客户资料、订单正文、账号、密码、Cookie、照片或登录状态。

## 环境与安全

- 明确 `B_photo`、可选 `B_pdf` 和业务根目录；系统当前时间只用于 PDF 时间门槛，不用于选择业务日期。
- 用户说明“当晚处理当天回传照片”时启用照片专用模式：使用当天实际业务日期目录，完成照片相关任务后结束，PDF 留到次日 10 点后另行明确执行。
- 优先使用 Codex 随附的 Python、NumPy、Pillow、pypdf、pdfplumber 和 Poppler。
- 使用 `assets/福单处理.atn` 中的“福单处理 / 福单压缩”，首次必须在副本验证。
- 用户亲自在 Codex 浏览器登录；不得索取、保存或自动填写密码。
- 任务进行期间使用独立只读页面定期刷新维持会话；不得刷新含未提交数据的表单，不得在任务结束后留下永久保活任务。
- 浏览器操作保持一个长期会话并按阶段批量完成；避免反复初始化、整页 DOM 快照、相同条件复核和等待 `networkidle`。筛选后使用每页 1000 条和表头全选，不逐条点击。
- NAS 业务根目录只保留日期目录、最终 PDF 和业务照片；不得创建、读取、恢复或迁移 `@自动化处理`。运行断点、日志、哈希凭据、备份、隔离文件和临时缓存全部写入本机非同步状态目录，且迁移包不得携带这些运行态数据。
- 每次完整初始化最多执行一次每日本机清理：未安全提交、需要回滚或异常任务的备份永久保留；每批照片处理写入完整提交回执后，原图恢复备份保留 7 天再删除，即使该日期仍等待后续补图也只清除已提交批次。staging 和 quarantine 必须等整个照片业务闭环满 7 天才删除。临时下载与 OCR 裁剪缓存保留 24 小时，历史计时报告每类保留最近 5 份；固定复用的 OCR 模型不删除。清理必须拒绝符号链接和越出本机 `祈福运行数据` 的路径，绝不扫描或删除 NAS 业务目录。
- 下载文件若扩展名仍为 `.crdownload`，只要文件头为 `%PDF-`、存在完整 `%%EOF` 且 pypdf 严格解析成功，即按完整 PDF 接管；不得继续等待永不结束的浏览器下载事件。
- “批量完成”“批量修改福单状态”和旧照片替换，在试运行阶段点击前取得用户确认。照片未齐时，该确认只授权当前筛选出的“福单已上传”订单；未上传订单不得混入。续费已处理终态在同批 PDF 与订单清单校验通过后自动执行，不再二次确认；只接受明确的终态确认文案或可见弹窗内部的终态选项，其他弹窗安全停止。
- 编号冲突、重复、上传回执数、系统匹配数或成功替换数不一致时立即停止。PDF 页数大于现有照片数时记录待补编号并继续处理现有可验证照片及其已上传订单；每批完成只要求该批“福单已上传”订单、场景图状态和订单 ID 清单一致，不要求照片总数与 PDF 页数齐平。整个日期闭环仍要求线上“福单未上传”为 0。
- 历史订单重新导出产生新编号时，不要求旧 PDF 编号形式上齐平；只允许在新增文件上传凭据完整、线上查询严格限定原 `B_photo` 且“福单未上传”为 0 时，记录旧编号已被替代。不得用执行当天或当前界面日期代替原业务日期，也不得从执行当天目录借用场景图；原业务日期缺少所需场景图时必须提示补齐该日期场景图后再继续。

## 工具

- `scripts/resolve_task_dates.py`：用显式 `B_photo`、可选 `B_pdf` 和任务模式解析目录与10点门槛，拒绝从执行时间推算业务日期。
- `scripts/match_pdf_photo_shapes.py`：仅在数字和文字不能唯一定位的疑难照片上运行，对近似纸张四角执行保守的多候选透视校准与稳定性聚合；默认不改名，可用 `--no-quad-refinement` 做旧算法对照。
- `scripts/validate_images.py`：校验工作目录或旧式日期目录 `1` 中的福单和场景图。
- `scripts/New-PrayerWorkday.ps1`：建立内部日志与清单目录。
- `scripts/merge_pdfs.py`：安全合并单类 PDF 分片并复核页数。
- `scripts/verify_downloaded_pdf.py`：验证仍以 `.crdownload` 命名的完整 PDF，并可在哈希一致保护下复制为正式文件。
- `scripts/track_workflow_timing.py`：记录隐私安全的阶段时间、计数器和异常事件，并生成可跨电脑持续优化的自我审计报告。
- `scripts/finalize_pdf_series.py`：按当天实际存在的纸色文件顺延命名。
- `scripts/finalize_business_day_folder.py`：确认当日最终 PDF 后写入 `M月D日` 并建立次日用的 `1` 文件夹，拒绝覆盖不同文件。
- `scripts/index_reference_pdfs.py`：建立源 PDF 文字与版式索引。
- `scripts/calculate_offering_quantities.py`：只读取当天最终 PDF 批次的唯一订单，换算实体灯并生成无括号说明的线下文案。

脚本必须使用绝对业务路径或显式参数。临时渲染和匹配文件写入本机非同步状态目录或系统临时目录，不写入 NAS 业务根目录或用户原始资料目录。

## 完成标准

- `B_photo` 已到照片与同业务日期 PDF 页面一一对应；数字、文字和必要时的指纹证据无冲突，重命名无重复、无未解决低置信结果。缺失照片可保留待补清单并形成部分完成状态；旧编号直接补传或历史重导出均以原业务日期线上“福单未上传”为 0 的凭据完成整个日期闭环。
- 图片上传数、系统匹配数、场景图和目标日期订单结果已核对。场景图真实路径已证明属于 `B_photo\1`，回执保存来源业务日期、路径、文件名和 SHA-256；任何执行当天或其他日期场景图均未混入。缺图批次中，当前“福单已上传”订单已经分批完成并保存图片集合哈希、订单 ID 哈希和完成数量；“福单未上传”订单仍保留待补。
- 若本次包含 `B_pdf`，其源页数、合并页数、连续序号及首页/末页已核对，并确保对应日期的 `1` 文件夹存在且原内容未受影响；照片专用模式不要求完成此项。
- 本次存在续费时，续费 PDF 已校验、同一订单 ID 清单已自动改为站点的续费已处理终态且原订单已全部离开未处理；回执记录实际采用的站点文案和弹窗模式，期间新到订单已留作下一批。若状态动作失败，明确保留可续跑断点且不重复导出。
- 续费新照片已确认替换旧照片。
- 供养物只按 `B_pdf` 最终导出订单汇总，线下顺序固定为：9元灯、3元灯、1元灯、供水，文本不带括号说明。
- 日志、形状匹配报告和异常清单只保留在本机非同步状态目录，NAS 中不存在工作流内部目录。
- 本机清理已留下只含删除项数、释放字节数和保留策略的匿名回执；未闭环任务备份、NAS 最终文件和固定 OCR 模型仍存在。
- `timing.json` 与 `timing-audit.json` 已生成；正常任务在对应模式阈值内，超时任务已明确记录原因和下一次优化项。
