# 祈福每日工作流

采用“人工触发 + 关键节点确认”。每次任务分别记录北京时间执行时间 `E`、照片实际业务日期 `B_photo`、可选的 PDF 业务日期 `B_pdf`。三者互相独立；不得根据任务发生在上午或晚上，把 `B_photo` 推算为前一天或当天，也不得把 `B_photo` 自动当作 `B_pdf`。微信保存、主观裁剪/补黑边、最终 PDF 对外发送仍由人工完成。

每次真实任务在第一次文件或浏览器操作前读取 `performance-audit.md` 并启动 `scripts/track_workflow_timing.py`。所有阶段、重试、人工介入和等待原因必须埋点；任务完成或安全停止时生成自我审计。

## 1. 日期与目录闭环

业务根目录沿用不带年份的日期文件夹：

```text
业务根目录/
├── 8月7日/
│   ├── 87供水.pdf
│   ├── 87红纸1.pdf
│   ├── 87黄纸1.pdf
│   └── 1/                 # 业务日期为8月7日的回传原图
├── 8月8日/
│   ├── 88供水.pdf
│   └── 1/                 # 业务日期为8月8日的回传原图
```

NAS 业务根目录到此为止，不得创建或恢复 `@自动化处理`。manifest、日志、索引、临时渲染、上传缓存、隔离副本和报告统一写入本机非同步状态目录，例如 `执行器上级目录/祈福运行数据/workdays/YYYY-MM-DD`；这些运行态文件不进入 NAS，也不打入迁移包。

本机状态目录使用分层保留策略：尚未安全提交、需要回滚或异常任务的恢复备份不自动删除；每批照片处理已经写入 `photo-prepare-receipt.completedAt` 且没有 `cleanupPending` 后，`photo-backups` 保留 7 天再删除。某日期仍等待后续补图时，也只清除已经成功提交批次的旧原图，不影响新增照片续跑。遗留 staging 和 quarantine 则必须等照片、场景图和牌位订单全部闭环且完成回执满 7 天后才删除。临时下载、OCR 裁剪和 PDF 编号裁剪超过 24 小时删除；每类历史计时报告只保留最近 5 份。OCR 语言模型是固定复用缓存，默认保留。完整初始化每天最多执行一次清理，并记录释放字节数；清理函数必须把目标解析到本机 `祈福运行数据` 内、跳过符号链接，禁止访问 NAS 业务目录。

- 常规例子：8月8日白天可读取业务日期为8月7日的 `8月7日\1`，同时另行导出明确指定为8月8日的 PDF。
- 晚间例子：8月8日晚处理业务日期为8月8日的回传照片时，读取 `8月8日\1`，本次仅执行照片分支，不生成任何 PDF；PDF 留到次日10点后在新的明确任务中执行。
- 图片在原 `1` 文件夹内处理并覆盖，不要求搬入另一套收件目录。
- 日期文件夹和 `1` 可能因用户提前放入当日回传照片而早于 PDF 存在；文件夹存在不代表 PDF 已导出。
- `B_pdf` PDF 导出成功后，确保对应日期文件夹及其 `1` 存在；若已存在则保留原图，不重建、不清空。
- 内部日志目录使用 `YYYY-MM-DD`，避免跨年混淆；业务日期目录仍按用户规则不带年份。
- 初始化不得只检查默认的“昨天”。扫描内部照片断点、待补编号清单和各日期 `1` 文件夹中的新增原图；多个日期未闭环时先处理最早日期。晚到照片仍归原实际业务日期，不归保存或执行当天。

任务开始时先运行日期解析器。晚间当日照片示例：

```powershell
python scripts/resolve_task_dates.py `
  --business-root "E:\业务根目录" `
  --mode photo-only `
  --photo-business-date 2026-08-08
```

该模式禁止传入 `--pdf-business-date`，输出必须为“不检查10点，不生成PDF”。次日需要 PDF 时重新使用 `pdf-only` 或 `combined` 并显式提供 `--pdf-business-date`。

## 2. 严格执行顺序

### 阶段 A：明确业务日期的照片上传，永远优先

阶段 A 不依赖当前时间，早于北京时间 10:00 也必须先执行。

1. 先发现全部未闭环照片日期，再从用户说明、原图所在日期目录、源 PDF 页面完整编码和系统业务日期共同确认每批 `B_photo`；不得只看执行时间。一次运行发现多个日期时，按日期从早到晚分别处理、分别查询和分别留回执。
2. 确认 `B_photo` 日期目录、`B_photo\1` 原图目录和 `B_photo` 的全部最终 PDF。
3. 解析全部源 PDF，优先读取首页、末页、页数和少量中间锚点。仅当 `末号-首号+1=页数` 且锚点顺序连续时，才按该区间生成中间页编码；否则逐页读取。全批仅有一个 OCR 离群值时，只有其余页构成唯一连续全集、全集恰有一个缺口、离群值与缺口仅一位字符混淆时才能修复并记录证据。不得从文件名后缀推算，不得补造因失败导出而缺失的编号。
4. 分类场景图和福单图。
5. 照片匹配采用逐级升级而不是全量双重计算：
   - 先独立识别照片右上编号；高置信且落在唯一 PDF 编号区间时直接定位；
   - 数字可能混淆（尤其 6/8）时，比较姓名、供养物、标题和版式等文字签名；
   - 数字与文字仍不能唯一定位时，才标记可信四角并运行形状指纹；
   - 形状脚本围绕近似框生成保守的纵向缩放/位移候选，以最强候选和前 K 候选稳定性共同评分；
   - 清晰照片不重复运行形状指纹，也不进行第二次人工逐张核查。
6. 最终只做一次全局一一对应检查，并把“缺照片”与“识别冲突”分开处理：
   - 一个 PDF 页面不得匹配两张照片；
   - 一张照片不得存在两个接近候选；
   - PDF 页面索引本身必须完整；照片可以暂时少于 PDF 页面，并把未匹配页编码写入待补清单；
   - 高置信数字唯一：采用对应 PDF 页编码；
   - 数字模糊但文字签名唯一：采用文字对应页编码；
   - 数字/文字仍不唯一但指纹唯一：采用指纹对应页编码；
   - 数字或文字与高置信指纹冲突、全部证据不足或重复：停止并写入异常清单，绝不猜号；仅缺照片时继续处理所有已唯一匹配照片。
7. 在副本验证 Photoshop 动作后，对原目录图片执行动作并原位保存。
8. 福单以完整编码最后一段命名为纯整数 JPG，不补前导零。
9. 场景图按识别类别和出现顺序命名：
   - 供灯：`2.1.jpg`、`2.2.jpg`；
   - 供水：`2.5.jpg`、`2.6.jpg`；
   - 超过两个或类别不明确时停止并提示，不自行扩展编号。
   - 历史补录时只能读取原 `B_photo` 日期目录下 `1` 文件夹中的上述场景图；禁止读取执行当天、照片保存当天或其他日期目录中的同名场景图。原日期场景图缺失时停止并提示补齐，不得自动寻找替代文件。
   - 不得把 4 张场景候选机械拆成 2 张供灯和 2 张供水；必须按视觉内容得到真实类别。出现 3 灯+1 水等超出每类两个命名位的情况时，明确列出多余类别并等待确认，场景歧义不得污染福单编号结果。
10. 校验 JPG、尺寸、比例和 1.5 MiB 上限。
11. 每批最多上传 50 张福单；照片未齐也先上传所有已唯一匹配且通过规格校验的现有福单。上传结果只读取原生弹窗与明确的消息层；忽略控件脚本、普通确认层全文和隐藏 DOM。若明确数字消息包含本批文件数以及页面累计数，只要本批精确数量至少出现一次，就以本批数量完成验证，不取最后一个累计数。上传回执按文件名和 SHA-256 逐张记账；旧式完整回执只有在文件集合哈希和总数同时一致时才自动迁移为逐文件哈希凭据。后续补图时跳过已有纯数字成品和哈希一致的上传记录，只识别、预处理并上传新增原图。月份选择页面完整编码对应的年月。点击上传控件前先建立 `filechooser` 监听，再一次性 `setFiles` 传入绝对路径；不得等待或操作 Windows 原生文件窗口。
12. 系统返回的文件数、匹配数和成功替换数必须与本批文件数一致。
13. 场景图和订单终态按已上传批次推进，不等待全部照片到齐：严格筛原 `B_photo`、福单状态“已上传”和订单仍可处理的记录，先处理“供水养净”，再处理其余供灯。打开浏览器前根据业务根目录和 `B_photo` 解析期望的 `M月D日\1`，使用真实路径验证每张场景图都直接位于该目录；真正设置上传文件前再校验一次。任一文件来自其他日期、符号链接指向其他目录或名称类别不符时，在任何上传/状态动作前停止。上传场景图后只批量完成本次筛出的订单。福单状态“未上传”的订单保持原状态并继续待补。每批保存场景图来源日期、真实目录、文件名与 SHA-256，以及图片集合哈希、订单 ID 哈希、完成数量和线上剩余未上传数量；重跑同一图片集合时先按回执和线上状态去重。旧 PDF 原编号补传时待补清单随补图逐项减少；历史重导出产生新编号时，只有新增上传回执完整且原 `B_photo` 线上“福单未上传”为 0 后，才能把旧编号记为“由重发/重导出结果替代”并把整个日期标记闭环。
14. 用户已明确授权本次上传或导出任务时，自动接受紧随该按钮出现的普通确认/提示弹窗，并在每次接受后验证上传数、匹配数或新下载文件。试运行阶段的“批量完成”“批量修改福单状态”或覆盖旧照片仍只保留一次终态确认；续费“代理已处理”已有长期自动授权，在同批 PDF 与订单清单校验通过后自动执行。

若本次被明确为“当日晚间只处理当日回传照片”，完成阶段 A 及其照片相关订单动作后立即结束。即使 `E` 已晚于10点，也不得进入 PDF 阶段，也不得生成供养物数量文案。结束前关闭计时并生成照片专用模式审计。

### 阶段 B：北京时间 10 点门槛

只有本次任务明确包含 `B_pdf`，并且应处理的照片任务已完成或明确不存在时，才检查时间。

- 使用时区 `Asia/Shanghai`，不得使用模糊的本地时区推断。
- 当前时间早于 `10:00:00`：提示“还不到北京时间10点”，保留现场并停止 `B_pdf` 的数据/PDF导出。
- 当前时间达到或晚于 `10:00:00`：继续阶段 C。
- 没有明确 `B_pdf` 时跳过整个时间门槛，不自动选择当前日期或照片日期。
- 10 点限制只约束 PDF 导出，不约束任何业务日期的照片上传。

### 阶段 C：导出明确业务日期的 PDF

1. 先明确 `B_pdf`；新订单的所有筛选必须同时包含状态“待祈福”和显式区间 `[B_pdf, B_pdf+1)`。已完成、祈福中或因特殊原因提前处理的未来订单必须排除。若本次运行先把已核对的待祈福批次改为祈福中，保存其唯一订单 ID 清单，后续导出只使用该清单。
2. 一次读取当前批次全部订单并在本地按供养物、模板和纸色分组；页面大小设为 1000，按筛选组使用表头全选，不逐条勾选。只有超过 1000 条才遍历分页。
3. 导出分组：供水、普通红纸、红色牌位、普通黄纸、黄色牌位。
4. 红色牌位使用“长生位模板”，黄色牌位使用“往生位模板”。
   - 牌位不能只看侧栏“待处理牌位”数字；进入牌位列表，严格筛状态“待祈福”且开始日期为 `B_pdf`。结果为 0 才跳过。
   - 长生禄位使用红色和长生位模板；往生莲位使用黄色和往生位模板。
   - 牌位没有场景图；回传福单图并核对后即可完成。
5. 每个新下载只做一次快速结构验证：文件头 `%PDF-`、结尾 `%%EOF`、pypdf 严格解析和页数。`.crdownload` 满足这些条件时视为完整 PDF；不等待浏览器下载事件。合并后复核源页数总和、最终页数和最终文件首末编号；只有编号识别失败或页数异常时才逐片视觉复核。
6. 当天所有业务板块共用红、黄纸各自的连续序号，只按实际存在的合并组顺延，不绑定业务类别，不覆盖已有文件。
7. 最终文件命名：`M月D日` 短码 + `供水/红纸N/黄纸N`，例如 `88供水.pdf`、`88红纸1.pdf`。
8. 将最终 PDF 放入业务根目录中与 `B_pdf` 对应的 `M月D日` 文件夹。
9. PDF 核对成功后确保 `M月D日\1` 存在；若用户已为当日回传照片建立该目录，保持内容不变。
10. 保存 PDF 页面文字索引、疑难照片形状报告、最终订单 ID 清单和最终 PDF 清单到本机非同步状态目录的 `workdays/YYYY-MM-DD`。复制到业务目录后只再核对一次大小和 SHA-256，不重复渲染；不得在 NAS 业务根目录建立内部工作目录。

最终 PDF 已位于当天目录时运行：

```powershell
python scripts/finalize_business_day_folder.py `
  --business-root "E:\业务根目录" `
  --processing-date 2026-08-08
```

若 PDF 先下载到内部最终目录，可加 `--copy-from`。脚本只在确认存在非空 PDF 后建立当天的 `1` 文件夹，并拒绝覆盖内容不同的同名 PDF。

## 3. PDF 快速索引与疑难照片形状指纹

### 页面清单

先读取首尾页、页数和锚点并生成显式页码与编码清单；只有连续性等式和锚点同时通过时才自动生成中间页：

```json
{
  "pages": [
    {"pdf": "87供水.pdf", "page": 1, "code": "268-1-179"},
    {"pdf": "87红纸1.pdf", "page": 1, "code": "268-1-184"}
  ]
}
```

右上角编码可能不是 PDF 文字层，可只渲染固定右上区域进行 OCR。文件名“红纸1/红纸2/黄纸1/黄纸2”不能用于推算编号段。失败导出可能消耗系统编号，因此不同下载片段之间允许存在有证据的编号缺口；保留审计记录，不伪造缺失页。

### 照片页面四角

为每张福单照片记录纸张四角，顺序为左上、右上、右下、左下。坐标可使用 0–1 归一化值：

```json
{
  "photos": [
    {
      "file": "微信图片_xxx.jpg",
      "candidatePdfs": ["87红纸1.pdf"],
      "digitCode": "184",
      "digitConfidence": 0.92,
      "quad": [[0.25, 0.30], [0.76, 0.29], [0.81, 0.91], [0.20, 0.92]]
    }
  ]
}
```

`candidatePdfs` 是数字和文字仍无法唯一定位后的疑难候选集合：先按标题、纸色、横竖版式和业务类别缩小范围，再在这些候选 PDF 页面内匹配形状。不要把无关红纸分片混在一起。

运行：

```powershell
python scripts/match_pdf_photo_shapes.py `
  --pdf-dir "E:\业务根目录\8月7日" `
  --page-map "...\pdf-page-map.json" `
  --photo-dir "E:\业务根目录\8月7日\1" `
  --photo-map "...\photo-map.json" `
  --output "...\photo-shape-matches.json"
```

默认只生成报告。只有报告满足以下全部条件才能再次使用 `--apply-renames`：

- 每张照片的最佳候选达到最低分；
- 自动分配页面也是该照片本身的局部第一候选；仅靠全局一一约束换位的结果必须人工复核；
- 第一和第二候选的分差达到最低阈值；
- 匹配编码不重复；
- 页面清单无缺失；
- 目标文件名不存在冲突。

`digitCode` 可写完整编码或末段数字；只有 `digitConfidence` 达到阈值才参与决策。没有可靠数字时留空，不得用猜测值填充。正常流程不把已有数字文件名当成 OCR；`--check-existing-numeric-filenames` 仅供迁移旧资料时选择性审计。

默认透视校准只在声明的四角附近做有限候选，不在整张照片中搜索，也不使用数字结果挑选裁切框。报告为每个候选页记录 `rectificationVariant` 和 `rectificationStableScore`。若需要与旧算法对照，可加 `--no-quad-refinement`；若自动校准后正确页仍不是局部第一候选，则重新标记四角或进入人工异常清单，不得调宽数字覆盖规则。

最终编号来自已验证的 PDF 页面索引。照片数字是快速路径，姓名/供养物等文字签名用于数字消歧，形状指纹只处理剩余疑难项。系统目标是“清晰项快速准确、疑难项升级验证、不能确定时停止”：只有全部证据严重不可用、证据冲突、照片重复或页面缺失时进入异常处理。

### 历史补图与重新导出

- 历史缺图直接重发旧 PDF 时，照片继续使用原编号，例如 333、334，并增量上传。
- 历史订单重新单独导出时，新 PDF 必须保存到订单原业务日期目录，照片使用新 PDF 的新编号；不得因导出发生在次日就改成次日业务日期。
- 无论使用旧编号还是新编号，补录订单的供灯/供水场景图始终取自订单原 `B_photo\1`；执行日只影响操作时间，不影响场景图归属。原日期没有对应场景图时停止，绝不借用执行日场景图。
- 每次现有照片上传后，严格按原业务日期分别查询“福单已上传”和“福单未上传”。先对“已上传”订单分批完成场景图和订单状态；“未上传”订单保留历史断点。只有“未上传”为 0 时才允许把旧 PDF 遗留编号标记为已替代并关闭整个日期。
- 初始化同时发现当日和历史补图时，先处理最早未闭环日期；每个日期独立保存 PDF 索引、逐文件上传凭据、线上未上传数和终态回执。

## 4. 图片规则

- 福单首选宽度 1800 px，保持比例，目标约 4:3，最大 1.5 MiB。
- 使用 `assets/福单处理.atn` 中“福单处理 / 福单压缩”。先在副本验证尺寸、画面和编号，再批量覆盖原图。
- 原图目录中只允许：纯整数福单名、`2.1/2.2` 供灯、`2.5/2.6` 供水；其他 JPG 名称在最终上传前必须解释或进入人工清单。
- 场景图由视觉内容分类，不依赖微信原始文件名；分类后的文件必须保存在其照片业务日期 `B_photo\1`，跨日期同名文件不可互换。

## 5. 供养物数量

只统计 `B_pdf` 当天最终导出 PDF 所包含的唯一订单：

- 以导出前保存的订单 ID 清单为准；重复下载、重复导出和未进入最终 PDF 的片段不重复计数；
- 不统计照片上传、批量完成或状态动作产生的操作日记录；
- 普通产品使用 `单个数量 × 数量`；缺少单个数量时按 1；
- 佛缘、莲花、往生灯名称中的 `7盏/49盏/108盏` 是每组数量；
- 莲花灯和往生灯合并计入 9 元灯，吉祥灯计入 3 元灯，佛缘灯计入 1 元灯。

线下文案固定为以下无括号、无额外解释的格式：

```text
师兄 今天
9元灯N盏
3元灯N盏
1元灯N盏
供水N份
辛苦您
```

## 6. 续费管理

1. 只筛续费处理状态“未处理”，不额外限定支付、开始或结束日期。
2. 红色使用长生位模板，黄色使用往生位模板。
3. PDF 序号接续当天同纸色已存在文件，绝不覆盖。
4. 核对页数、页面编码和形状后发送。
5. PDF 通过结构、页数、文件哈希和原始未处理订单 ID 清单校验后，自动重新核对当前未处理清单哈希，再改为续费已处理终态，不再要求第二次点击。站点终态文案兼容“延续已处理”“代理已处理”和“已处理”：
   - 点击“批量修改处理状态”后若出现明确的“确定要批量修改成…已处理状态”确认框，直接确认，不要求不存在的下拉框；
   - 若可见弹窗内确实存在状态下拉框，只在该弹窗内部选择终态；禁止扫描或操作页面上的“延续处理状态”筛选下拉框；
   - 弹窗既无终态选项又无明确终态确认文案时安全停止，不提交修改。
6. 提交后再次查询未处理清单，原订单 ID 必须全部消失才写入本批完成回执；回执同时保存实际终态文案和弹窗模式（直接确认或下拉选择）。提交期间新到的不同订单保留为下一批，不得混入本批或误判本批失败。若原订单仍存在或状态动作失败，保留已校验 PDF 和原订单哈希，下次只补做状态变更，禁止重复导出。
7. 回传照片使用数字/文字快速路径，只有疑难项才运行 PDF 页面形状匹配，再走统一上传入口。
8. 核对上传数、匹配数和成功替换数；替换旧照片前保留人工确认。

## 7. 登录保活

系统空闲超时时间未知。仅在当前任务进行期间：

1. 使用独立保活标签页打开系统主页或其他只读页面。
2. 约每 5 分钟没有业务请求时，对该只读页面执行一次安全刷新或导航请求。
3. 不刷新包含已选择文件、未提交筛选或未保存表单的业务页面。
4. 每次业务操作前检查是否被重定向到登录页。
5. 一旦登出，停止上传/状态操作，要求用户本人重新登录；不得读取、索取或保存密码。
6. 任务完成、暂停或等待用户超过当前执行回合时停止保活；不得创建永久后台绕过会话超时。

### 浏览器提速与弹窗

1. 每个业务阶段使用一个长期浏览器会话，避免反复初始化、重新认领标签页或重复读取整页 DOM。
2. 等待具体元素、行数变化、弹窗或新文件，不等待 `networkidle`。
3. 上传前先监听 `filechooser`，再点击并设置绝对文件路径。
4. 对已授权的上传/导出动作，点击后短轮询并自动接受紧随其后的普通 `confirm/alert`，最多处理两个；随后必须验证结果。
5. 下载通过下载目录中新文件和 PDF 结构判定，不等待浏览器下载事件完成。
6. 同一筛选条件未发生状态变化时不得重复核验；读取一次订单清单后在本地完成分组、数量和去重。

## 8. 人工确认与停止条件

- PDF 页编码无法目视确认。
- 数字或文字与高置信指纹冲突，或全部证据都不足；仅照片数字模糊但文字或指纹唯一时不停。
- 疑难照片页面四角无法可靠标记、形状分数低或候选过近且文字/数字不能完成安全消歧。
- 照片重复、PDF 页面索引不完整、目标文件冲突，或已到照片无法唯一匹配。仅“尚未收到全部照片”不停止现有照片的重命名、上传和已上传订单分批完成；历史重导出只有在原业务日期线上未上传为 0 时才允许把旧编号标记为已替代并关闭整个日期。
- 需要主观裁剪或补黑边。
- 系统上传数、匹配数、替换数不一致。
- 批量完成、批量状态修改和旧照片替换之前。续费代理已处理已由用户长期授权，在同批 PDF 与订单清单校验通过后自动执行。
- PDF 对外发送之前。

## 9. 任务结束与自我审计

1. 关闭最后一个运行阶段并完成计时记录；不得把用户阅读或长期等待计入主动处理阶段。
2. 设置照片数、PDF页数、最终导出订单数、三层匹配数量、浏览器动作、重连、人工介入、重试和重复验证计数器。
3. 运行 `track_workflow_timing.py finish` 和 `audit`，把 `timing.json`、`timing-audit.json` 保存到内部工作日目录。
4. 正常任务超过照片专用10分钟、PDF专用6分钟或完整闭环15分钟时，必须说明最慢阶段和证据，禁止仅写“页面慢”。
5. 审计只输出一至三项下一次可执行优化；连续三次稳定后再写回技能规则并提升版本。
6. 写入任务终态后不立即删除恢复备份；由下一次完整初始化按上述 7 天恢复窗口统一清理。清理失败只记录本机维护异常，不回滚已经完成的线上业务，也不得扩大删除范围重试。
