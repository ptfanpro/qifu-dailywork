# 识别与业务绑定重构设计（部分保护已接入、非发布说明）

## 为什么必须分开

历史实图证明：照片上的完整码可被两个引擎正确读出，却与当前 PDF 中的另一页同号。继续提高数字识别准确率，并不能独立解决这种关联错误。数字是一次打印的索引，不是永久订单身份。

## 三层证据

| 层 | 内容 | 禁止行为 |
| --- | --- | --- |
| 原始观察 | 原图 SHA-256、裁框、引擎/模型版本、纸面完整码、原始得分 | 不得按当前 PDF 编号集删除“范围外”观察；不得把引擎得分伪造成正确概率 |
| 文档修订 | PDF 内容 SHA-256、页码、该次打印编号、经校验的订单 ID 集合摘要 | 不得以同一天或同文件名视为同一次打印；不得按页数猜未读编号 |
| 业务绑定 | 原图哈希 → 原打印修订/页 → 同一订单集合 → 当前修订/页 | 不得以纸面编号等于当前编号替代归属验证；不得仅凭顺序补齐绑定 |

所有真实订单映射和回执仍保存于本机非同步运行目录，不能进入 Git、公开日志或模型请求。跨电脑缺少映射时，先通过已有只读方式核对线上状态；不擅自复制 Cookie、凭据或推测已经上传的内容。必要的历史人工映射必须绑定照片和 PDF 内容哈希，并保留审计记录。

## 历史材料分流

1. 有经过校验的原始打印清单：按打印修订解析纸面码，再按同一订单集合定位当前页。
2. 只有当前 PDF，但存在经过人工核对、内容哈希完整的旧映射：复验文件未变化后保留映射；新的 OCR 观察不能直接覆盖它。
3. 编号与正文存在冲突、修订来源缺失：保持未决，进行本地正文比对和必要的人工复核；不让错误目标进入上传计划。
4. 某张未决不应使已经独立确认、互不冲突的照片全部重新识别。未决项不能被标为已完成。
5. 场景图走独立类别/日期绑定。背景出现蜡烛不能覆盖真实纸张/编号证据，也不能因为只剩一个场景名额就强行分类。

## 回归必须覆盖

- 同一纸面编号，在两个修订中对应不同正文：无修订证明时拒绝自动绑定。
- 旧纸面 448 对应新 PDF 446：保留有完整证据的旧映射，不自动改为当前 448。
- PDF 同名同大小但内容变化：旧索引失效，上传回执保留并重新对账。
- 两个引擎同读一个数字，但正文/订单归属不同：不能以“双引擎通过”放行。
- 两个引擎同读的 40/8 分别落入当前 PDF 中错误的页面，实际正文对应 48/6：完整数字及索引存在性都不能代替内容绑定。模糊原图不够确认纸面原数字时，保留“误读或修订差异未分清”，不要编造原因。
- 一个引擎的相反完整码不得被另两个引擎的多数票或 PDF 允许集合抹掉。仅有方法名和引擎名称、缺失实际观察，也不得快速确认。
- 同引擎重复读取、相似模板、编号遮挡、两张照片争用同页、同步替换和跨电脑缺回执：分别记录原因，禁止静默猜测。
- 独立复核空结果、范围外码和中途异常保留在提议之外；后续成功方法名或缺号推断不能删除先前失败。单锚点模板扩展也须检查强相反候选，不能只在多锚点分支检查。

## 实施边界

本文件是审计后形成的重构方案，不代表上述文档修订/订单绑定层已经接入执行器。旧资料没有完整打印清单时不能凭空补造。是否增加面向未来打印件的机器可读标识，应在本地 PDF 输出规则确认后单独实施；本轮不修改服务端打印模板、不部署后端、不更改用户现有 PDF。

原始观察层中的严格完整码、冲突保留、来源检查已经分批接入；这不等于第三层业务绑定已实现。简单正文 SIFT 实验在新增真实反例中把错误页排在前面，因此也尚未接入产品。

独立复核的失败历史现已在审计分支接入 `codeAuditHistory`，它不会因后续提议重写而丢失；当前同一计划内不能用一次自动重试清除此类未决。用户发起重新检测时会生成新的识别计划。该机制不是全部 OCR 路径的不可变原始观察层，也不替代跨 PDF 修订的业务归属证明。

### 中文正文试验（仍未接入产品）

新增隔离中文检测/行识别，再与当前所有 PDF 页的正文文字层比较，不向 OCR 提供纸面目标码或历史文件名。最初三个数字共识与正文冲突的真实样本取得了正确正文候选；远景供水也出现正确候选但特有文字很少。该实验只生成诊断排名，不改绑定或赋号。不能把两个视图叫作双引擎，不能把重叠四字片段当作独立投票，也不能把 OCR 得分当正确概率。

生产接入前仍须覆盖：相同地址/姓名跨页、共用模板、正文重复、PDF 缺文字层、只读到背景字、纸张遮挡以及当前修订改变分单边界。若旧页订单分裂到当前两页，即使部分文字匹配，也不能重命名成其中任一页；只有完整对应证明或人工确认才能推进。实际打印修订/订单 ID 清单链仍不能由文字最高分替代。

完整正常批次对照已暴露适用范围：30 张福单中 23 张有稳定正文候选，7 张没有特有正文；其中包括竖版和稀疏模板。不得把“正文缺证据”改写成“确认数字错误”，也不能一律要求这一路径才可继续。另一方面，正文确有冲突时，数字共识不能覆盖它。需要明确保存可用、不可用、冲突三种证据状态，再按打印修订、字段覆盖和订单集合证明作出绑定；不能仅通过调整四字片段数量阈值交付核心重构。

竖排补充路径仅在离线试验启用。诊断必须同时保留横排/竖排视图，并拒绝把“稳定第一名但另有页面正文”写成单一候选；它仍不能证明旧页与当前页的完整订单集合相同。即使某页正文非常清楚，也可能只看到了同一地址或同一客户的一部分内容。

### PDF 文字层不等于完整可见正文

真实牌位 PDF 中，固定模板文字在完整页面上可见，却不在 `getTextContent` 的提取结果里；相同文字在普通福单页上可能是可提取文字。因此“只在一页文字层出现”不等于“只在一页实际页面出现”。加入照片中文 OCR 而不审计 PDF 侧正文来源，会把模板文案误认成另一页特有证据。

新增离线 A/B 试验对全部候选 PDF 页读取文字层及完整页面图像，以来源独立的片段集合并集计算共用性。不能只补目标页，不能拼接不同来源制造片段，不能以读取过程完成代替可见字段完整覆盖。这一来源补充尚未接入产品，更不等于跨修订订单绑定已经完成。

### 9 月 8 日正文否决保护（候选代码，未部署）

`body-content-review.mjs` 已在实际计划形成数字提议后、生成最终改名/上传范围之前接入。共用中文读取、PDF 可见语料和汉字片段原语移入 `src`，原试验入口保留转导出；试验指纹同步覆盖这些真实依赖。固定中文检测/识别模型随候选源码资产携带并逐次校验哈希，不要求网络下载。

正文保护只否决，不自动赋号。全部当前 PDF 页文字项与完整可见渲染按来源分别比较；照片横竖四视图均保留。任何不同页的特有文字不能被更高排名取消；同布局两视图都支持其他页标为正文冲突，仅单视图出现也保留待核。不读取历史参考答案，不把正确正文排名直接写成新编号。

正文历史独立于数字提议，后续数字共识、补号、场景分流不能抹掉。现有数字文件、数字修复和规格归一化也必须经过该保护；被扣留的现有数字文件从本次允许上传集合排除。模型缺失、语料页身份不完整或读取失败时不能以“没有发现冲突”为由通过。报告只有内容哈希、页身份和计数，没有中文原文。

限制：`observed-body-consistent` 仅表示本次观察未出现其他页面的特有正文，`no-specific-body-evidence` 表示证据不足；两者都明确 `bindingVerified=false`。目前这两种结果保留原有数字路径，尚未取得完整订单集合或原打印修订证明。因此这一否决层不是完整业务绑定重构，不能宣传为所有错配已杜绝，仍需真实回放和后续覆盖/修订绑定工作。

### 续跑时的文件身份（候选代码，未部署）

`photo-plan-gate.mjs` 在真实上传/场景入口检查混合目录的计划是否过期，并要求当前数字/场景文件的内容与已审阅原图或精确处理回执一致。处理回执必须证明同一业务日期、计划之后的处理时间、相同源目录/哈希、完整的分配与重复来源，以及正确目标名称/类别和成品哈希。普通原图初始化不因此开启 OCR；不变成品的完整回执可直接复用，未分配原图不能借此进入上传集合。

只读重新核对可能提出改号，但尚未实际改名的数字原图不能按旧名继续上传。扫描后的待上传文件哈希再次与计划/回执对照，原有提交前集合检查继续保留。真实 JPEG 事务联测覆盖回执结构，不把纯函数模拟当完整处理联测。

这些检查证明的是“当前这份文件就是审阅或处理过的文件”，不是“这张照片属于正确订单”。正文缺失、原打印修订不明和完整订单集合未核对等限制仍由上层证据策略解决，不因输入哈希一致就宣称第三层业务绑定通过。
