# 周末问题复盘与验收边界

本次从 v9.6.7 建立修复分支，不从部署副本开发。原图、PDF、客户正文、运行凭据未纳入 Git；未执行生产上传或订单状态变更。

## 根因与证据

1. **编号定位覆盖缺口（旧问题）**：原算法主要沿固定横向位置上下搜索。真实完整编号横跨中间窄带右边界和右侧宽带左边界，前者截尾号，后者截前缀/混入装饰。相同 ONNX 模型在完整号码裁剪中能读出；因此不能把问题简单归因于 Windows OCR 或照片不清楚。
2. **场景角色判定依赖全图阈值（旧问题）**：周末两张暗场灯阵受视角/边缘密度影响，未进入场景路径，被送往福单编号 OCR。增加分散暖色亮点的空间结构证据，但清晰业务编号和可用矩形纸面保持优先，不能凭缺图数量猜场景类别。
3. **重复计算（旧问题）**：最多 304 个旧裁剪区每次都重读原图、解码 JPEG、写临时 PNG。新代码每张只读/解码一次，内存裁剪；新二维覆盖的窗口数量有明确上限。同批只复用优先检查位置，不复用号码或识别结果。
4. **在线状态衔接不严谨（旧风险）**：检索导航超时被吞掉，未证明响应/请求/落地筛选一致就读取表格；“先查零、后来查到待办”的周末现象缺少原始请求证据，不能断言平台延迟是唯一原因。现在请求与落地条件、响应状态、分页数量都必须相符。场景上传按实时缺失集合有限次续跑，最终非零不得批量完成。
5. **未知上传结果误当失败（旧风险）**：无数字回执且集合暂时不变，不足以证明第一次失败。删除自动第二次提交；先有限次只读核对。提交前持久保存不确定状态，重启也不擦除；全部订单已上传才能据精确集合认领成功。
6. **跨电脑运行态互相污染（已确认配置缺陷）**：原程序将运行数据放在程序父目录；现场该目录是同步占位/重解析目录，且出现另一电脑盘符设置。新运行态固定到 Windows 当前用户 LocalAppData 下的 `PrayerDailyRunner/祈福运行数据`，检查祖先重解析点，不回退 NAS/程序父目录；UI、命令行和 OCR 缓存一致。旧目录保留，不自动导入断点或加密凭据。
7. **同模型双视图重复误读（原图复现）**：一次完整回放发现真实 68 被读成 58，与另一张真实 58 冲突。彩色/归一化两票来自同一个模型，PDF 索引存在也不是独立内容确认。冲突时围绕已发现的号码位置缩窄横向、轻微移动纵向，交叉调用不同本地引擎；至少两个引擎各在两个不同物理裁框读出同一完整业务前缀/编号才接受。真实 68 已由 Paddle 与 Tesseract 独立确认；没有添加“缺 68 就把 58 改成 68”的猜号规则。两个独立结论冲突时仍拒绝确认。

## 测试门槛

- 全量历史 Node 回归、Windows UI 状态、进程安全、本机路径与加密存储测试。
- 本地 Edge 表单：正常查询、日期被改变、HTTP 500、没有提交；后三者必须拒绝读取旧表为零待办。
- 编号二维覆盖、同模型双视图与独立引擎明确区分；同模型两票、同一裁框重复计票、两个独立候选冲突均不能冒充独立确认。裁剪前后逐像素哈希一致（正常与 EXIF 旋转样例）。
- 暗场结构正例、单一黄色矩形/单排亮点反例、清晰业务编号优先级。
- 迟到的已上传状态、第一次场景查询跳过后出现待办、持续非零、查询异常；不进行未知结果重传。
- 本地原图只读回放：输出匿名计数、耗时及源文件前后集合哈希；完整私人诊断仅在本机临时目录。

## 版本治理发现

抓取远程后发现：本地部署基线已到 9.6.7，但远程 main 仍是合并到 9.5.82 的主线。记录过提交/标签并不等于修复已统一进入主线。远程与本机的旧 v9.5.81 标签指向不同对象；本轮不得强制覆盖该历史标签。新修复从 9.6.7 分支保留完整历史，通过正常合并/PR 集成主线，使用独立的新候选标签。

本轮已在修复分支正常合入远程 main，并推送修复分支。创建 PR 时 GitHub 连接返回 403（无创建权限），因此没有创建 PR，也没有直接修改 main；需要仓库维护者创建合并申请。未尝试使用其他凭据绕过限制。

## 升级注意

本轮全量 Node/Windows/隔离 Edge 回归通过。完整本地回放为 26 张照片、23 页 PDF，得到 23 张福单、2 张供灯、1 张供水，缺号、重复、阻断项均为 0，源文件哈希未变，耗时 254 秒。样本组成是 21 张备份原始福单，加 2 张后补福单及 3 张当前场景；后补/场景副本均改为非数字测试文件名，实际执行 OCR/分类，不利用已有规范文件名绕过识别。该耗时包含索引和场景识别，不是控制条件一致的性能基准。

另一次五日角色回放共 91 张，仅有 3 张已有场景从旧规则漏判变为场景，没有新增数字福单变成场景。仍未执行生产上传、状态修改或三次生产稳定性验收。

周六原始批次追加回放通过：16 张照片、13 页 PDF，得到 13 张福单、2 张供灯、1 张供水，缺号/重复/阻断项为 0，源文件哈希未变，耗时 282 秒。使用 12 张原始备份（11 张福单及 1 张供水）和备份缺少的 2 张福单、2 张供灯现有文件；新增副本均使用非数字测试名。早先组装样本误加了两张已在备份中的福单，重复保护正确拦截；纠正的是临时验收素材，不是通过更改算法吞掉重复。原始 49 号照片成功识别，压缩成品负例仍如实保留。

负例/已知限制：将周六现有压缩成品全部去掉规范数字文件名后重做首次 OCR，16 张得到 12 张福单及 3 张场景，1 张未决。该张压缩图的前缀 269 被主引擎读成 209，独立完整前缀证据不足；未按唯一缺号补成 49，也未降低校验标准。此测试不同于真实原始照片入口，也不同于保留编号及回执的正常续跑。不能声称“任何压缩成品均可无损重新识别”；原图及已验证回执仍应保留。相关近似前缀放行尝试未采用，候选仍保持两个不同引擎、各两个完整前缀裁框的冲突确认要求。

- 入口名称、照片默认北京时间昨天、PDF 默认北京时间今天、人工验证码流程不变。
- 换电脑后各自选择可用业务目录、各自登录；不复制断点、Cookie 或加密凭据。旧同步运行数据不删除，不能直接当新电脑成功凭据。
- 历史业务先查询线上。已有 PDF 没有本机绑定凭据时不重复导出、不猜订单关系；需要先完成凭据核对。
- 本次离线通过不等于生产全过程或未来所有照片已经验证。按 DEVELOPMENT.md，连续三次真实稳定运行后才切换默认桌面入口；候选包不能冒充这一验收结果。
- 本轮没有升级工作流技能版本，没有移除证据冲突的安全停止规则，没有降低唯一编号/订单集合核验要求。
