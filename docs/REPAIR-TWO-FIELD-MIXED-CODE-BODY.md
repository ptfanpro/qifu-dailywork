# 强编号与两字段正文闭环修复

## 问题

一张历史疑难照片已有完整编号的强原始读数，编号在当日 PDF 索引中唯一；正文复核也在同一 PDF 页发现一个长字段和一个三字短字段。长字段在照片 OCR 中与少量噪声、数字或标点落在同一个检测行，旧逻辑虽然能读取正文，却不能把该长字段绑定到物理裁框，因而保持未决。

即使正文判定成功，后续 PDF 二次复核还会先要求灰度页面指纹。代码/正文联合证据本来已经绑定完整 PDF 字节、页码和编号索引，这个无关前置条件会把有效结果误判为“PDF 页面不唯一”。

## 修复边界

新增判定仅适用于已经通过原有强完整编号门槛的候选，并且同时满足：

- 编号在完整当前 PDF 索引中只对应一个物理页面；
- 一个至少四个汉字的 PDF 长字段同时来自 PDF 独立文本项和两种同版式可见 PDF 读数；
- 该长字段在照片检测行中只出现一次，行内最多另有两个零散汉字，不能存在另一个三字以上语义字段；
- 另有一个独立的三字短字段，同样由 PDF 独立文本项和两种可见 PDF 读数共同确认；
- 两个字段在两种照片视图中均落在各自相同检测区域，且物理裁框不重叠；
- 两个字段组合只属于目标 PDF 页面。

缺号推断、前缀修复、日期修复、弱编号、相反编号、连续更长汉字、重复目标、同一区域、重叠裁框、其他页面包含同字段或任一读取失败时均保持未决。序列化后的结果没有跨进程授权能力，恢复时仍需原回执和来源哈希。

代码/正文联合证据的 PDF 二次复核现在直接复核其已经绑定的完整物理 PDF 字节和编号索引，不再要求无关的灰度指纹；其他编号方式仍保留原有灰度指纹门槛。

冻结包验证同时暴露出旧发布门槛在 Windows PowerShell 默认执行策略下会拒绝加载测试脚本。发布门槛现显式使用 `-ExecutionPolicy Bypass`，只作用于该测试子进程，不修改系统或用户策略；回归测试固定了完整命令参数。

## 验证

- 两字段/三字段判定回归：4 个正例、39 个拒绝检查通过；
- 实际收集器、来源替换、部分语料、旧冲突与跨进程恢复回归通过；
- 历史真实入口重新读取 45 页 PDF 和 1 张疑难照片，缓存命中 0，成功完成判定及物理 PDF 二次复核；原始编号读数未修改，外部操作 0；
- Windows 全套回归通过：主测试 239/239，以及长路径 OCR、中文/英文模型、检测缓存和浏览器查询集成。
- 发布门槛的 Windows PowerShell 调用参数回归 7/7 通过。

以上仅确认该缺陷类别的局部闭环，不代表整日回放、全年验收或发布验收完成。
