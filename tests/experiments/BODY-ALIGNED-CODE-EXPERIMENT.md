# 正文位置回投编号：失败保留与白边对照

2026-09-11。本次是只读诊断，不修改生产识别、原照片、订单、默认日期或固定入口。此前 20 张未决照片中有 17 张分散正文位置支持；**本次没有把其中任何一张改为编号已确认**。完整产品结果仍是 `0d1daf9` 的 73 张、51 分配／22 未决。

## 固定回投与失败

`body-aligned-code.py` 从独立正文位置的归一化单应矩阵回投既有 PDF 固定编号窗口。窗口由物理页面方向选择，不输入 OCR 答案、历史名或缺号。镜像、奇异矩阵、投影极点、越界均拒绝；不通过裁掉越界部分补成成功。

- 17 张 × 两窗口，两个引擎分别读取 PDF 参考图和照片投影，共 136 项。照片四项同码 1/17，参考图四项同码 0/17，两边共同同码 0/17。编号区是正文拟合外推，未证明完整字符范围。
- 红通道二值化、首条连续两行长横线分离对照共 68 个裁图，51 个找不到符合条件的横线、17 个不能证明文字与线分离，0 个输出。没有降低横线门槛或把贴线笔画删除。
- 新增生成反例先暴露了“空行下面还有文字接到横线，却被裁掉”的实现漏洞；修正为分隔空行必须紧接横线之前。Python 7/7；原几何 Python 6/6。

这些是新诊断工具的问题和边界，不能倒推成已修好所有生产照片的根因。

## 内嵌图片与分割模式对照

Pypdf 读取四份 PDF 的 69 个物理页，发现 72 个短宽编号图对象。三处相同像素在同一位置重复绘制，不能当独立证据。原型只对本批实际旋转、MediaBox 和绘制矩阵作检查；不替代既有 `pdf-image-candidates.mjs` 的最终可见页面逐像素校验。几何选择前两次遇到重复对象失败，原输出保留；第三次按字节、绘制矩阵及尺寸去重，未按识别结果挑对象。

按实际内嵌矩形回投 17 张照片，再用双引擎读取 PDF／照片，共 68 项：照片双引擎同码 3、PDF 双引擎同码 3、两边共同同码 1。私有结果旧字段名 `allFour...` 有显式说明：本子试验每侧实际两个读数，不是四个。

随后固定比较 72 个 PDF 原图与 17 个照片投影：无白边／四边各六像素白边，分别用 Tesseract 单行／单词／原始行模式；共 89 × 6 = 534 项。没有向引擎提供月份、尾号或参考答案，旧读数没有被覆盖。

| 输入及固定单行模式 | 唯一完整码 | 同时达到 30 分 |
| --- | ---: | ---: |
| PDF 无白边 | 69/72 | 20/72 |
| PDF 六像素白边 | 72/72 | 72/72 |
| 照片无白边 | 7/17 | 6/17 |
| 照片六像素白边 | 9/17 | 0/17 |

PDF 白边结果达到 50 分的为 71/72，不是全部；照片白边分数均为零。单词／原始行没有改善。以上分数只描述观察，**不是修改生产阈值，更不是识别正确率**。72 个 PDF 读数与冻结计划的同一物理页索引一致（69 页、差异 0），该索引不是独立人工真值。

直接提取编号位图、加白边的思路不是本轮首次提出：此前[最终页可见位图试验](PDF-IMAGE-CANDIDATES-EXPERIMENT.md)已用十二像素白边验证 99 页。当前是进一步固定参数对照，不能将不同白边、不同分数和不同样本数混算成新的成功率。照片未获改善，不能把 PDF 白边规则直接套到照片。

## 核验、计时与下一步

独立核验重新哈希原 73 张照片和四份 PDF，重建 534 个实际引擎输入、重新解析全部保存读数；89 个无白边单行基线与之前输入哈希、原文和置信度逐项一致。参考计划哈希不变，照片冲突清除 0。

初始回投源码哈希为 `00f86dc00d9787078d9349dc71c35bbd67cb95846c6aad362bfde8235cd4976d`；之后在同一文件增加横线分离函数。核验器按明确的新增声明／函数边界重建原始源码前缀，哈希精确相同；这不等于当时保存过完整独立文件快照。

完整 Windows 普通回归 155/155、无跳过；实际 OCR、模型、缓存、日期、UI、进程和浏览器模拟通过。统一发布门槛重新运行仍因三个原有场景反例失败，退出 1。没有升级版本号、创建发布标签或切换入口。

下一步须复用已有最终页可见性提取器，验证白边对照的物理页身份和跨日期表现；照片端需另行解决完整码冲突，不能用 PDF 单独读得更好来授权照片改名或上传。所有诊断输出仍 `mayAssign=false`、`mayClearCodeConflict=false`。
